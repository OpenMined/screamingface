# OME-466 — url4 serve: minimal CLI to run the engine as an HTTP node

## Intent

> **SUPERSEDED (2026-07-16) — historical.** This was the intent at work START, before both
> pivots. The aigateway connector, the `url4[serve]` extra name, and the Starlette/uvicorn
> quarantine below are all obsolete: the extra is **`url4[server]`** (uvicorn only, Starlette
> never added), and `url4 serve` ships **no aigateway connector** — `[commands]` is the only
> backend kind. Current intent: the "Scope extension (2026-07-16)" section.
> *This ledger is a chronological record — superseded sections are marked, not rewritten.*

Expose the framework-free `url4` engine as a runnable **url4 node** via a minimal CLI +
HTTP server, shipped as an optional `url4[serve]` extra on `packages/url4`. A user runs
`url4 serve` to stand up an endpoint that evaluates url4 expressions — fanning out model
calls to the aigateway (`:9105`) and dispatching custom/command routes locally — realizing
the doctrine's "url4 expression IS the address" node model (N1/N4/N5) at the SDK layer.
Companion `url4 eval` gives a network-free one-shot. Keeps the core import graph
framework-free (Starlette/uvicorn quarantined behind the extra, like `io_http` quarantines
httpx).

## Scope extension (2026-07-16) — commands-only serve + `default_route` (owner-directed)

### Intent

Owner decision on the same branch/PR: `url4 serve` stops shipping an aigateway
connector. Routes and commands are the same thing at the SDK core (an endpoint), so
the serve layer keeps ONE concept: `[commands]` — user-owned subprocess argv
templates (a user who wants an LLM backend writes their own gateway script and
mounts it as a command). The serve-layer `processor` config is renamed
`default_route`; it must name a declared command route (ConfigError otherwise) and
defaults to the FIRST declared command route. Empty `[commands]` → fail-fast
ConfigError. Core SDK keeps the `processor` NAME but loses the hardcoded
`"/claude"` default: unset means "first registered endpoint" on `Url4Node` and
"no reduce route — clear ResolutionError on fan-out reduce" on the bare engine.

### Planned changes

- `src/url4/_serve.py` — DELETE the aigateway connector: `DEFAULT_ROUTES`,
  `make_llm_handler`, `_extract_content`, `_merge`, `build_client`,
  `_resolve_token`, `_flag_routes`, `_CHAT_PATH`, the `httpx` import, and the
  `backend_url`/`backend_token`/`routes` config fields. `ServeConfig.processor` →
  `default_route: str | None = None` + `resolved_default_route` property
  (explicit value, else first command). `validate()`: commands non-empty;
  explicit `default_route` ∈ commands; reserved-path checks now against commands
  only. `build_node(config)` / `build_asgi_app(node, config)` lose the client
  param; lifespan closes the node only.
- `src/url4/cli.py` — drop `--backend-url`/`--backend-token`/`--route`;
  `--processor` → `--default-route` (env `URL4_DEFAULT_ROUTE`, toml
  `default_route`); `_SERVE_FIELDS` updated.
- Core (name kept, selection behavior changed): `dag/node.py` — remove
  `DEFAULT_PROCESSOR`, `ExecutionContext.processor: str | None = None`;
  `dag/executor.py` — `run(processor: str | None = None)`, ctx-clash guard on
  `is not None`; `dag/nodes.py` — `FanoutReduceNode.resolve` raises
  `ResolutionError` when `ctx.processor is None`; `client.py` —
  `Client(processor: str | None = None)`; `server.py` — `Url4Node(
  default_processor: str | None = None)` resolves unset → first registered
  endpoint at eval time, explicit-but-unregistered → `ResolutionError`.
- Tests: rewrite `tests/unit/{test_serve_config,test_serve_backends,
  test_serve_app,test_cli}.py` for the commands-only world (owner-approved
  append-only exception); append core tests (`test_dag.py`, `test_server.py`,
  `test_client.py`); update any prior core test that pinned the implicit
  `"/claude"` default (mandated by the owner's core-behavior decision — each
  one listed in the Outcome).
- Docs: revision notes in `docs/spec/2026-07-15-url4-serve-spec.md` +
  `docs/plan/2026-07-15-url4-serve.md`; `docs/tasks/2026-07-15-url4-serve.md`

## Scope extension 3 (2026-07-18) — the node's READ surface + protocol params (owner-directed)

### Intent

`url4 serve` could declare only the **write** half of an expression. `[commands]` gave the node
intent processors, but a served node had **no sources**: a bare relative URI (`(/rubrics/42)`,
spec §5.4.2) had nothing to resolve against, and `@` / `@name` (spec §5.6) failed with "serves
no holdings". `Url4Node` has always had the `data()`, `holdings()` and `identity()` registries —
the serve layer simply never wired them, so the capability was reachable from the SDK and
invisible from `url4.toml`.

Second, smaller gap: a command backend saw only `{intent}` and `{context}`. The protocol params
a caller sends (`/model?temperature=0.7`) reached a *Python* endpoint handler via
`Request.params` but were invisible to a *command* route — a second-class backend in a design
where a command is the only backend that ships.

**Why this folded into OME-466 rather than becoming a new work item.** Owner's explicit
direction, and it holds up against the confidence gate: this issue's stated goal is "expose the
engine as a runnable url4 node", and a node that cannot resolve `@` or a relative URI does not
meet it. This is the same unit finishing, not a new one starting. Recorded here because the
default under the card would have been a fresh OME-N + ledger.

### Planned changes

**A. Code** (`packages/url4/src/url4/_serve.py`):
- `ProviderSpec` — one declared read backend: exactly one of `value` / `file` / `command`, plus
  `media_type` for `[data]` only. One shape for all three registries, so a read backend follows
  the same operator-owned model as a command route.
- `ServeConfig` gains `data` / `holdings` / `identities`, TOML-only like `commands`. Collection
  keys normalize `"default"` → `None` (TOML has no null key; `None` is the node's fallback
  shelf).
- Parse (`_toml_data_map`, `_toml_shelf_map`, `_toml_identity_map`, `_as_provider`) and validate
  (data path shape + clash with commands/reserved; identity names against the node's own
  `_IDENTITY_NAME_RE`) — every failure a pre-bind `ConfigError`, never a build-time `ValueError`
  from `Url4Node._check_routable`.
- `_provide` + `make_data_provider` / `make_shelf_handler` / `make_identity_handler`; `build_node`
  registers all three registries.
- `make_command_handler` — `{param:<name>}` and `{params}`; substitution moves from chained
  `str.replace` to a single regex pass.

**B. Docs** — spec §1/§5/§7/§8/§9/§10, plan (signatures, layout, build order, test doubles),
task mirror, this ledger.

## Follow-up (2026-07-18) — the "uvicorn test fragility" was a silent suite hang

**Supersedes** the gate note in "Outcome (scope extension 3)" above (which recorded *794 passed,
2 failed* and called the two failures benign) and follow-up #1 from review round 2.

### What it actually was

`test_cli.py::test_serve_forever_without_uvicorn_prints_hint` and
`test_server.py::test_serve_requires_uvicorn` assert the *missing*-`uvicorn` branch. Both did it
by calling the real seam and **relying on the ambient venv to lack the `[server]` extra** — the
comment in the first said so outright: *"The dev env has no uvicorn."* Neither test created the
condition it asserted.

Once the extra was installed, `importlib.import_module("uvicorn")` succeeded, so
`cli._serve_forever` skipped the error branch and called the real `uvicorn.run()` with
`object()` as the ASGI app: it started a server process, bound `127.0.0.1:4404`, and served
forever. **`pytest` hung — no failure, no timeout.** Confirmed by killing the run at 25s
(`exit 124`).

For most of this ticket it *looked* like a fast, harmless failure (`errno 98 address already in
use`) — but only because an unrelated `url4 serve --config demo/url4.toml` (the owner's demo,
pid 3178783) happened to hold 4404. **The symptom depended on an unrelated process.** That is
why three review rounds classified it as "fragility, CI is green" instead of what it was: any
developer following `README.md` (`uv sync --extra server`) on a machine with 4404 free wedges
their suite, and CI would too the moment it installed the extra.

### Fix

- `tests/conftest.py` — **`hide_uvicorn`** fixture: wraps `importlib.import_module` so *only*
  `uvicorn` raises `ModuleNotFoundError`. Both tests take it and now pass with or without the
  extra, because they create their own precondition.
- `tests/conftest.py` — **`_no_real_listen`** autouse guard: any `socket.listen` from a unit test
  raises immediately with an actionable message pointing at `hide_uvicorn`. Binding stays legal
  (ephemeral sockets, `socketpair`); *listening* is what makes a test serve forever. This turns
  the whole bug class from a silent hang into a 0.02s failure. Verified with a throwaway test
  that tries to listen — refused as intended.
- `tests/unit/test_cli.py`, `tests/unit/test_server.py` — take the fixture; comments corrected.

### Result

- **796 passed, 0 failed**, with `uvicorn 0.51.0` installed and 4404 free — the exact condition
  that hung before. `run_gates.py url4 --skip-append-only`: **ALL GATES GREEN**.
- **Rule 5 / append-only:** this edits two *prior* tests, so the gate is red without
  `--skip-append-only`. Per rule 5 that is a Confidence-Gate decision, and it was taken
  explicitly by the owner ("properly think about it and solve it") after the hang was
  demonstrated. Every other test in this unit remains append-only; the skip covers exactly these
  two files.
- Follow-up #1 from review round 2 is **closed**, not deferred.

### Wisdom

- **A test that depends on an ambient environment fact is not testing what it says.** The
  precondition must be created by the test. `hide_uvicorn` is four lines; the missing four lines
  cost three review rounds of misdiagnosis.
- **A misleading symptom is worse than a loud one.** The bug was masked by a coincidence (a
  stray process holding the port), which made every observation of it wrong. When a failure's
  mode changes depending on unrelated system state, that instability is itself the finding —
  chase it before classifying the bug.
- **Documenting a hazard is not fixing it.** This was carried as a "known follow-up" through
  three rounds and two documents, each round restating it more precisely. The owner's correction
  — *solve it, don't write about it* — was right: the fix was smaller than any one of the
  paragraphs describing it.
