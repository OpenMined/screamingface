# OME-684 — PR review: scope reduction and the Cloudflare correction

Supersedes parts of the four earlier OME-684 ledgers. Where they disagree with this one, this one is
right — read this first.

## The correction that reframes the rest

The earlier ledgers, the commit messages, the PR body and my comment cancelling `OME-588` all claim
this work "is not Cloudflare" and that Cloudflare Access was "abandoned". **That is wrong.** Re-read
of https://pulse.dev.openmined.org/docs/products/gateway-identity-flow/ :

- Cloudflare Access authenticates the caller at the edge — human OTP *and* service tokens.
- It issues the assertion in `Cf-Access-Jwt-Assertion` and forwards through a `cloudflared` tunnel.
- **Envoy re-verifies that assertion against Cloudflare's JWKS** (`<team>.cloudflareaccess.com`)
  and translates the verified claims into plain headers.

So the identity IS Cloudflare identity. What actually changed versus `OME-588`/`OME-591` is *where
the JWT is verified* — Envoy, not aigateway — which is why the `cf_access/` JWKS package those
issues specify is genuinely unnecessary. The mechanism was not abandoned; it moved.

## Changes (owner decisions, PR review)

1. `GatewayIdentity` → `CloudflareIdentity`; `gateway_identity.py` → `cloudflare_identity.py`;
   `AIGW_AUTH_MODE=gateway_headers` → `cloudflare_headers` (one vocabulary, 19 files).
2. Dropped `X-Tenant`, `X-Service-Id` **and** `X-User-Id`. `X-User-Email` is the whole identity.
   - Tenant is redundant once the key is an email — emails are globally unique.
   - Service-token callers now get a 401. Accepted: automation is out of scope until gateway-issued
     API keys (`OME-592`). Pinned by a test so re-adding it is a visible decision.
3. `account_for_identity` uses `Account.get_or_create`. Verified rather than assumed: Tortoise
   1.1.7's `get_or_create` → `_create_or_get` creates inside a transaction and re-fetches on
   `IntegrityError` — identical protection to the hand-rolled version, which is now deleted.
4. The account key is the **username**, which is the email. The derived `uuid5` id is gone. It cost
   nothing: credentials key on `account.id`, which is stable for the row's lifetime, so a unique
   username plus `get_or_create` gives the same stability more simply.

## The one that bit — migration 0008

Widening `accounts.username` 64 → 255 (RFC 5321 allows 254; Postgres enforces `VARCHAR` length,
SQLite does not, so the failure would have been prod-only).

The obvious `ops.AlterField` **destroyed data**, and `test_migration_populated_db` caught it: SQLite
cannot widen in place, so Tortoise rebuilds the table — `CREATE TABLE new__accounts` … `DROP TABLE
accounts` … `RENAME`. `oauth_connections.account_id` references `accounts` with `ON DELETE CASCADE`,
so that DROP deletes **every OAuth connection in the database**.

Fix: dialect-guarded raw SQL via `ops.RunPython` — the ALTER runs on Postgres, and SQLite does
nothing. That is not a workaround for the cascade; the cascade exposed that SQLite never needed DDL
at all, because it does not enforce `VARCHAR(n)`. Both dialect strings verified against Tortoise
(`sqlite`, `postgres`), and both branches are now unit-tested with a recording schema editor.

SUPERSEDED — the paragraph below stated the consequence and then accepted it. Accepting it was
wrong, and the follow-up section corrects it.

> KNOWN CONSEQUENCE: `RunPython` contributes no state change, so migration state records
> `max_length=64` while the model says 255. Nothing at runtime reads it — migrations here are
> hand-written and `python -m tortoise migrate` only applies them — but an autogenerated migration
> would propose the widening again. Delete that proposal rather than applying it twice.

## The trap that acceptance left behind (fixed)

"Delete that proposal" is an instruction to a future maintainer who has no reason to suspect the
proposal is dangerous. Reproduced against the installed Tortoise 1.1.7: `makemigrations` did propose
`AlterField(Account.username)` again, and applying that generated migration to a populated SQLite
database performs the same table rebuild and the same `ON DELETE CASCADE` wipe of
`oauth_connections` — a deterministic data-loss trap, armed, invisible in any diff.

The fix splits the two halves `AlterField` normally couples. `0008` now declares a
`WidenUsername(ops.AlterField)` operation that KEEPS the inherited `state_forward` — so the
projected state moves to 255 and the autodetector goes quiet — and overrides only
`database_forward`/`database_backward` with the dialect guard. `RunPython` is gone.

Pinned by `test_autodetector_proposes_no_account_change`, which fails if the state half is ever
dropped again.

NOT fixed, and out of scope: the autodetector still proposes `AlterField(OAuthConnection.account)`.
That drift **predates this branch** — verified by running the same probe at the merge-base with
`main`. It is a Tortoise artifact: the live model's FK resolves `source_field`/`to_field` during
`Tortoise.init` while the migration-projected copy does not, so the pair never converges. The test
asserts it exactly, so a genuinely new drift cannot hide behind it.

## The one that was FATAL — the run path still demanded a bearer token

Found by reading `runner/main.py` after the fact. Each of the earlier units verified its own half;
none exercised the combination production actually runs — identity present, token absent. In that
combination the deployed stack **could not execute a single run**.

The chain, all verified in code:

1. `url4.toml:24` declares `[aigateway]` and is baked into the image, so `section is None` never
   happens in a real deployment.
2. `runner/main.py` raised `RunnerConfigError` when a declared section had no `AIGATEWAY_TOKEN`.
   Pinned by `test_a_declared_gateway_without_a_token_fails_inside_execute`.
3. `AIGATEWAY_TOKEN` had exactly one source: the inbound `Authorization` header on `GET /`. It was
   in `WRITTEN_BY_APP`, never `DEPLOY_TIME` — no chart-supplied fallback existed.
4. In `cloudflare_headers` mode `current_account()` dispatches to `_account_from_cloudflare_headers`
   and **never reads `Authorization`**.
5. The chart removed aigateway's public Ingress, so a caller had no reachable route to obtain a
   token in the first place.

⇒ a Cloudflare-authenticated caller got `RunnerConfigError` → `Terminated(failed)` → **502 on every
run**. `GET /v1/models` was dead the same way: it 401'd without a bearer token no deployed caller
could get.

## The fix — the token is gone entirely (owner decision)

Owner ruling: local deployments run aigateway with `AIGW_AUTH_MODE=disabled`. That leaves the token
with **no reader in any supported configuration** — `cloudflare_headers` reads `X-User-Email`,
`disabled` treats every caller as anonymous, and `jwt` is not a supported setup. So it was removed
end to end rather than made conditional:

- `job_env.AIGATEWAY_TOKEN` deleted; `job_env.SECRET` is now an empty (but retained) frozenset, so
  `test_job_env_contract` keeps guarding the by-reference rule for whatever is added next.
- `rest/_credentials.py` deleted — `Authorization` is no longer read anywhere in this app.
- `K8sJobRunner`: no per-run Secret, no `secrets_client`, no `CoreV1SecretsClient`, no
  `min_job_ttl_s`. `credential` is still accepted (the port lives in `packages/url4`, which stays
  untouched) and is deliberately dropped — pinned by a test.
- `InProcessJobRunner`: the ambient-token fallback is gone. `AIGATEWAY_PROFILE` now resets from the
  ambient env the same way identity already did — previously an ambient profile could leak onto a
  run whose caller never asked for it.
- The chart's `Role` loses its `secrets` verbs entirely.
- `X-Profile` is forwarded on its own merits instead of only alongside a token: it selects WHICH of
  the resolved account's credentials to use, which is orthogonal to who the caller is.

`GET /v1/models` works in both deployments: `Credential` carries identity + profile (no token), and
the identity is part of the cache-key material so two callers cannot share an entry.

## Deviations — both deliberate, both worth challenging

1. **A documented invariant was dropped.** `/v1/models` used to reject an unauthenticated request
   before calling upstream, so it "cost aigateway nothing" (spec §11 acceptance 2). That was only
   sound while a token was mandatory. url4-cloud cannot know aigateway's auth mode, and an absent
   identity is legitimate in `disabled` mode — rejecting locally would make the endpoint permanently
   unusable in dev. Anonymous requests now reach aigateway, the only component that knows whether to
   refuse them. Remaining flood protection: `catalog.cache`'s entry cap and single-flight bulkhead.
   Carries an `AIDEV-NOTE` at the site.
2. **~12 prior tests were deleted, against the append-only rule.** They asserted the behaviour just
   removed (Secret creation and teardown, token forwarding, bearer-absent 401s, `min_job_ttl_s`
   construction). The rule's escape hatch is that an obsolete test is a finding to surface, not to
   quietly edit — so it is surfaced here. Each was replaced by a test pinning the new invariant: a
   supplied credential is DROPPED, no Job env entry may carry `valueFrom`, and an anonymous caller
   never shares a cache key with an identified one.
