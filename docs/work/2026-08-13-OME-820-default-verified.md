# OME-820 — default new submissions to verified (ran on OpenMined infrastructure)

## Intent

`verified_by_openmined` defaults to `False`, and **no HTTP route can set it** — only an uncalled
`store.mark_verified()` helper exists. With the re-run verification service (`OME-414`) still in
Backlog, every row on the board therefore reads "unverified" permanently. Ahead of Monday's tester
cohort that reads as broken rather than cautious, so the 2026-08-13 huddle asked for the default to
flip (`[52:20]`).

Flipping a boolean is trivial; deciding **what the flag then claims** is not, because that claim is
published. This unit changes the default *and* re-defines the field's meaning so the claim stays
true.

## Decisions locked (2026-08-13)

| # | Decision | Choice |
|---|---|---|
| D1 | What "verified" asserts | **"This run executed on OpenMined infrastructure"** — not "OpenMined independently re-ran a submitted recipe". Owner decision. For the Monday cohort this is literally true: testers run against the hosted SF Engine, through OpenMined's AI Gateway, on OpenMined's capped keys. There is nothing to independently reproduce because the numbers are already ours. |
| D2 | Rejected alternative | Flipping the default while keeping the old "we reproduced this" meaning. That would make the database assert a reproduction that never happened, and once `OME-414` lands a defaulted row would be **indistinguishable** from a genuinely reproduced one. The board's headline claim is that it is verified, so a false positive here is a product-integrity bug, not a cosmetic one. |
| D3 | Rejected alternative | Hiding the distinction in the UI only (storage stays `False`). Rejected because the API would keep returning `false` while the board implied otherwise — two sources of truth disagreeing, and `OME-771` would inherit the mess. |
| D4 | Client cannot self-declare | `verified_by_openmined` **stays absent from `ScoreSubmission`**. A submitter must never be able to assert its own trust tier. `extra="forbid"` already rejects it; this unit pins that with an explicit test rather than relying on the config staying put. |
| D5 | No backfill | Existing rows keep `False`. Marking historical rows verified would assert something about runs nobody checked — and some existing rows are local test submissions that did *not* run on OpenMined infrastructure. If the demo needs particular old rows shown as verified, that is a deliberate data operation, not a schema default. |
| D6 | Scope boundary | The self-reported case (BYOK, local/packaged execution) is **not** handled here — it is `OME-821`, filed as blocked by this ticket. Once a non-OpenMined execution path ships, this default becomes wrong and `OME-821` must land with it. |

## Planned changes

- `apps/scoreboard/src/scoreboard/scores/models/score.py` — `verified_by_openmined` default `True`,
  with the WHY/INVARIANT anchors recording D1 and D5.
- A migration under `apps/scoreboard/src/scoreboard/scores/migrations/` generated by the built-in
  Tortoise CLI (`uv run tortoise makemigrations --name default_verified_true`; Tortoise 1.1.7,
  **never Aerich**; config resolves from `[tool.tortoise]` so no `-c` flag). Ships this iteration
  per stack rule S1.
- `apps/scoreboard/src/scoreboard/routes/scores.py` — the module docstring currently states the
  opposite ("submitted scores default to unverified regardless of how the submitter
  authenticated") and must be corrected, along with the `get_score` docstring.
- Tests under `apps/scoreboard/tests/unit/`.

No change to `ScoreSubmission`, the store's write path, the read DTOs, or the portal: the field is
already carried end to end, so only its default and its documented meaning move.

## Test plan

RED first:

- **Default:** a submission omitting the field is stored `True` and reads back `true` on
  `GET /v1/leaderboard/{id}`, the per-spec history, and `GET /v1/scores/{id}`.
- **D4 invariant:** a submission that *sends* `verified_by_openmined` (either value) is rejected
  `422`. This is the integrity test — without it, a client could badge itself verified.
- **D5:** a row created with `verified_by_openmined=False` still reads `false` after the change —
  proving the new default applies to new rows only and nothing was backfilled.
- **Regression:** `store.mark_verified()` still sets `True` and is idempotent on an already-verified
  row.
- **Migration:** applies from an empty database; a second `migrate` is a no-op; `makemigrations`
  reports no drift afterwards.

### Deviations

1. **There is no migration, and that is correct.** `uv run tortoise makemigrations` reports
   **"No changes detected"**: a Tortoise `default=` is applied in Python at instantiation, not as a
   database-level `DEFAULT` clause, so flipping it alters no schema. The plan anticipated this and
   required it be recorded rather than worked around — a hand-written migration here would have been
   a no-op at best. Stack rule S1 is satisfied: there is no schema change to ship.
   **Consequence worth knowing:** because the default is Python-side, any row created by raw SQL
   still gets whatever the database column default is, not `True`.
2. **Four prior tests on `origin/main` asserted the old contract** and were flipped `is False` →
   `is True`, one line each, with a comment saying why:
   `test_leaderboard_routes.py:111`, `test_sf_payload.py:87`, `test_scores_routes.py:130`,
   `test_store.py:102`. Escalated as a Confidence-Gate decision per sdlc rule 5 and **owner-approved**
   rather than edited on the strength of "breaking contracts is fine". Nothing was removed or
   weakened, and unverified coverage is *preserved* by the new explicit-`False` row test — so the
   suite can still catch a regression in the other direction. The final gate run therefore used
   `--skip-append-only`; every other gate ran normally.
3. **Two of my own new tests failed for the wrong reason first.** I omitted the `tortoise_db`
   fixture, so they errored with `ConfigurationError: default_connection ... cannot be None` rather
   than on the assertion. Caught by reading the failure instead of assuming RED meant the feature was
   missing — worth noting, since a fixture error masquerading as a genuine RED would have let a
   broken test through.
4. **The default has a documented expiry condition.** It is honest only while every execution path is
   OpenMined's. `OME-821` is filed and linked `blocked-by` this ticket, and the model carries an
   `AIDEV-NOTE` pointing at it. Local packaging (`OME-678`, PR #559) was reported at the same huddle
   as landing by EOD, so this is days away, not hypothetical — the PR body must say so.
5. **No PR opened yet** — awaiting owner approval; nothing outward-facing sent.

### What was wrong with my design

D1 said verified means "ran on OpenMined infrastructure", justified by asserting the cohort
runs on the hosted stack. That is an assumption about usage, not something the write path
establishes. My own spec §3 forbids a *client* declaring its trust tier; defaulting to True
had the server assert a tier it cannot verify, which is worse because it looks
authoritative.

Finding 2 was the merge-stopper: the portal defined the badge as a rerun, so the default
would have published a false claim on every row, in the same commit that rejected it.

### The fix (owner chose option A)

Kept it to four lines of substance rather than redesigning:

- `portal/index.html` and `portal/benchmark.html` — the reproduction claim is withdrawn.
  Both now say scores are self-reported and the column does not yet distinguish rows.
- `models/score.py` and `routes/scores.py` — docstrings corrected. The field asserts
  **nothing**; it is a placeholder. Both carry the invariant that the default and the
  portal copy must change together.

Confirmed: only two files ever made the reproduction claim, and **no test pinned that
wording**, so nothing else had to move.

Not fixed, deliberately: finding 1's attestation gap. It needs a mechanism that does not
exist (`OME-821`). What changed is that the board no longer claims what it cannot support.
